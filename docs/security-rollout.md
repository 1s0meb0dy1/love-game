# Исправления аудита: проверка и выпуск

Изменения клиента сохраняют существующие ID, AES-ключи, ссылки, расположение сессий и совместный доступ по секрету. Работающая база и опубликованные Rules из этой среды не менялись.

## Что изменилось

- Восстановление профиля завершается перед первой записью. Записи сериализованы и используют Firebase ETag/If-Match. При конфликте облачная копия не перезаписывается; локальный прогресс остаётся на устройстве, показывается уведомление. Флаг конфликта сохраняется после перезагрузки; выбор облачной копии выполняется явно в «Игроки и сессия».
- Удаление останавливает новые операции текущей сессии и ждёт уже начавшиеся profile/join/analytics/live-записи. Содержимое сессии, старого пути, join-code, аналитики и live-комнаты заменяется пустым маркером `deleted: true`. Маркеры не содержат имён, AES-ключа сессии или прогресса и не должны автоматически удаляться: они нужны для защиты от повторной записи.
- Новые клиенты распознают маркеры. Запрет их перезаписи старыми версиями требует новых Rules. Локальные копии на других, особенно отключённых устройствах, удалённо стереть невозможно.
- Очистка устройства относится к текущей сессии: удаляется и её старый v3-профиль; ссылки на другие сессии и общие настройки сохраняются.
- Миграция старого XOR-формата сначала сохраняет AES-копию и join-code, затем удаляет старую копию. Неудачная миграция сохраняет старый путь для повторной попытки.
- Ходы live публикуются условно по ETag; конфликтующая история объединяет завершённые действия игроков. Команды старой партии не применяются к новой.
- В статистике учитываются завершённые ответы/пропуски. Клики во время рулетки не пропускают карточку.
- Аналитика отправляет `ownerUid` и ссылку `sessionRef`; новые Rules проверяют неизменяемое авторство и запрещают новые записи статистики удалённой сессии, даже под новым ID. Маркеры удалённой аналитики также нельзя заменить отчётом. Чтение аналитики остаётся только владельцу проекта.
- Новые персональные вопросы сохраняют `aud_…`, выведенный из 128-битного ключа, вместо кода входа. Это выбор аудитории интерфейса, а не шифрование текста: сам публичный `/questions` остаётся доступным. Скрытые вопросы тоже сохраняют редакционное, а не конфиденциальное значение.
- ИИ-запросы отменяются при выходе, поздние ответы игнорируются, реальные имена не нужны для советов, GET с текстом запроса удалён. Офлайн-подсказка больше не содержит вымышленных процентов.
- Обновлены Vite/React plugin/PWA и уязвимые вложенные зависимости. Минимальная среда проекта — Node 22.12+; используемая Node 22.23 подходит. CSS проверен сравнением вывода до и после обновления парсера.

## Локальная проверка

```sh
npm ci
npm run verify
```

В средах, где pipe дочернего Node возвращает пустой вывод:

```sh
TEST_CAPTURE_FILES=1 npm run verify
```

Режим сохраняет вывод тестов во временных файлах и проверяет также код завершения процесса. В случае ошибки runner печатает путь к журналам.

Для проверки правил нужны Java 21+, Firebase CLI и доступ к загрузке официального Database Emulator с `storage.googleapis.com`:

```sh
npm run test:rules
```

Тесты используют только `demo-love-game` и локальный Database Emulator. Они не подключаются к рабочему проекту. Проверяются доступ без Auth, owner-only контент, сохранение совместного чтения известной сессии, запрет перечисления, типы/размеры, неизменяемость аналитики и невозможность восстановить удалённые узлы.

В текущей среде загрузка `firebase-database-emulator-v4.11.2.jar` заблокирована сетевой политикой. Поэтому шаблон новых Rules пока считается **не прошедшим проверку движком Firebase** и не должен публиковаться до успешного `npm run test:rules`.

## Порядок выпуска

1. Сохранить резервную копию базы и опубликованных правил (владелец уже сделал backup). Не добавлять экспорт с именами и секретными адресами в Git.
2. Успешно выполнить UI/unit/build/size проверки и тесты Emulator. Проверить два браузера: создание, ID/ссылка, продолжение партии, одновременный ответ/пропуск, уход/возврат ведущего, удаление во время медленного запроса.
3. Подготовить согласованный выпуск клиента и Rules; старые версии нужно обновить, особенно перед удалением данных. Новая версия клиента уже совместима с текущими Rules, однако прежние версии не умеют добавлять `ownerUid` и отправляют персональный `targetId` открытым текстом.
4. Подтвердить перенос исторической аналитики. Записям без `ownerUid` нельзя безопасно автоматически назначить произвольного первого заявителя. Владелец может архивировать старую статистику и удалить старые ownerless-записи; активные обновлённые устройства создадут свои записи заново под тем же локальным `aid`. Удалить старые `sid` из архивных записей. Административное чтение исторических записей останется доступным, но обычный клиент не сможет менять запись без подтверждённого владельца.
5. Сформировать настоящий файл правил с UID текущего владельца из опубликованных Rules:

   ```sh
   npm run rules:render -- --owner-uid <UID_ВЛАДЕЛЬЦА>
   ```

   Команда только создаёт игнорируемый `firebase/database.rules.json`. UID — идентификатор для проверки токена, не пароль. Шаблон `OWNER_UID` нельзя публиковать без замены.
6. После проверки реального UID, результатов Emulator и плана миграции опубликовать только Database Rules явной командой с project ID:

   ```sh
   npx -y firebase-tools@latest deploy --only database --project project-x-5e16a
   ```

   Эта команда в ходе исправлений **не выполнялась**. Автоматическая публикация GitHub Pages следует текущему CI репозитория после push в `main`; push в ходе работы не выполнялся.
7. После выпуска проверить сценарии со старой и новой сессией и убедиться, что маркер удалённой сессии не заменяется активными данными. Откат одного только клиента не отменяет новые Rules: для отката потребуется согласованная версия обоих компонентов. Откат правил, запрещающих восстановление удалённых узлов, снимает эту защиту.

## Что не входит в автоматическое исправление

Настройки MFA владельца, ограничения Firebase API key, App Check, серверные квоты и выбор политики хранения требуют доступа к конфигурации проекта и отдельной проверки доступности. Клиентские задержки не заменяют серверные квоты. Количество вновь создаваемых сессий текущая схема Rules глобально не ограничивает; для этого нужен доверенный сервер или иной механизм выдачи сессий.

Большой UI-файл не переписан целиком: выделены координаторы записи, а стабильные экраны сохранены. Полная архитектурная миграция и переход от REST polling к Firebase SDK — отдельные изменения с дополнительной проверкой совместимости.
